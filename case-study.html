Case Study: Credit Card Fraud Risk Scoring (CRISP-DM)

This case study demonstrates how CRISP-DM can be applied to a real-world fraud risk scoring problem.

Demo tip: Point out the structure: each phase shows inputs → processing → outputs, which matches the rubric’s “data inputs, processing steps, tools, outputs, correct sequencing”.

Problem summary (1 minute overview)

  • Context: A bank processes many card transactions daily.
  • Problem: Fraud losses happen when fraudulent transactions are not detected quickly.
  • Goal: Predict fraud risk in near real time and trigger an alert for high-risk transactions.
  • Output: A risk score (0–1) + “Alert / No Alert” decision, plus a monitoring dashboard concept.

This aligns with Week 8’s CRISP-DM case study theme: reduce losses by detecting fraud and focusing evaluation on the right metrics (paraphrased).

1) Business Understanding

Business question: “Which transactions should we flag as fraud risk right now?”

Inputs

  • Stakeholder goals: reduce fraud losses
  • Constraints: avoid blocking too many legitimate customers
  • Operational reality: investigators can review only a limited number of alerts

Processing

  • Define success criteria (KPIs) and acceptable tradeoffs
  • Decide what “fraud” label means (confirmed chargeback, verified case)
  • Set an alert policy (e.g., alert top 1% risk scores)

Outputs

  • Problem statement + scope
  • Evaluation priorities: focus on catching fraud (low false negatives)
  • Deployment target: fraud alert + daily monitoring report

2) Data Understanding

Here I check what data we have, whether labels are reliable, and what patterns look suspicious.

Inputs

  • Transaction log: amount, timestamp, merchant category, country, device ID
  • Customer profile: account age, typical spend range, home country
  • Fraud label: confirmed fraud / not fraud

Processing (EDA)

  • Check class imbalance (fraud is rare)
  • Find missing values (e.g., device ID missing on some channels)
  • Look for anomalies: sudden high amounts, unusual locations, rapid repeat purchases

Outputs

  • Data quality notes (missingness, duplicates, inconsistent categories)
  • Early insight: fraud clusters around unusual country + high amount + short time gaps
  • Plan for preparation: handle imbalance + engineer behavior features

3) Data Preparation

This is where messy raw logs become a clean modeling table. In practice this stage is often the most time-consuming, because small data issues can break the model later.

Inputs

  • Raw transaction + customer tables
  • EDA findings: missing fields, rare categories, imbalance

Processing

  • Cleaning: remove duplicates, fix invalid timestamps, handle missing device ID
  • Transform: encode categories (merchant type), scale numeric amount if needed
  • Feature engineering:
    • Transaction speed: time since last transaction
    • Amount deviation: amount vs customer’s typical average
    • Geo mismatch: country differs from usual location
  • Imbalance handling: stratified split + class weighting (or careful sampling)
  • Train/validation/test split (example: 70/15/15)

Outputs

  • Model-ready dataset (rows = transactions, columns = features)
  • Feature list + data dictionary (short documentation)
  • Saved split sets (train/val/test) for reproducibility

Week 8’s fraud example mentions imbalance and engineered features like speed/deviation + scaling (paraphrased).

4) Modeling

I test multiple models, because “best” depends on metrics, cost of errors, and interpretability.

Inputs

  • Prepared training/validation sets
  • Baseline expectation (simple model first)

Processing

  • Baseline: Logistic Regression (fast, interpretable)
  • Stronger model: Random Forest (handles non-linear patterns)
  • Optional: SVM if dataset is moderate and features are scaled
  • Hyperparameter tuning using validation set (e.g., tree depth, class weights)
  • Choose a probability threshold for “Alert” based on investigation capacity

Outputs

  • Candidate models + validation scores
  • Selected model (example choice: Random Forest with class weighting)
  • Feature importance / explanation notes for stakeholders

5) Evaluation

In fraud detection, I care a lot about catching fraud cases (reducing false negatives), but I also don’t want to flood investigators with false alarms.

Inputs

  • Test set predictions
  • Business constraints (review capacity, customer friction)

Processing

  • Metrics: precision, recall, F1-score
  • Confusion matrix to see false positives vs false negatives
  • Threshold tuning: choose alert threshold that balances recall with workload
  • Risk review: bias, drift risk, and what data might change over time

Outputs

  • Final performance report (example target: high recall with acceptable precision)
  • Decision: ready to deploy as “risk scoring + alert”
  • Documented limitations (e.g., new fraud patterns may reduce accuracy)

In fraud detection, recall and false negatives are especially important because missed fraud can cause high losses.

6) Deployment

Deployment doesn’t have to be complicated. The key idea is: results must be used in the real workflow.

Inputs

  • Approved model + threshold
  • Integration target (fraud operations team)

Processing

  • Generate risk score per transaction
  • Trigger an alert if score ≥ threshold
  • Log decisions for auditing and retraining
  • Monitoring plan: track performance + drift + retraining schedule

Outputs

  • Real-time alert concept (API-style) + daily summary report
  • Simple dashboard: alerts/day, top merchants, precision/recall trend
  • Maintenance checklist (monitor → retrain → version)

Demo line: “CRISP-DM ends with deployment so the insight becomes business value, not just a model file.”
